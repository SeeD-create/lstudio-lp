貴所で再現していただけます

権限の強制は、アプリケーションではなくデータベース側（PostgreSQL の行レベルセキュリティ）で行っています。 そのためアプリケーションに不具合があっても、担当外の行は開きません。 検収の場では、次の2行を貴所に打っていただく形を想定しています。

-- 職員 S01（東さくら。顧問先 K001 のみ担当）として接続する
SELECT set_config('app.shokuin_id', 'S01', false);

-- 担当外の顧問先 K002 の案件を、顧客IDを直接指定して取りにいく
SELECT * FROM urizun.anken WHERE kokyaku_id = 'K002';
--  → 0 rows

接続に使うロールは NOSUPERUSER / NOBYPASSRLS で、 認可の根拠となる担当表・職員表への書き込み権限も外してあります。判定に使うのは所内の担当表と在籍状態だけで、 AIが出力した顧客IDは認可条件に一切使っていません。

ただし、この行の 'S01' はアプリケーションが設定する値です。 データベースの接続情報そのものをお持ちの方は、任意の職員を名乗れます。ここは守れていません。 本番では、認証済みのセッションからのみこの値を設定し、接続情報は鍵の管理に載せます。 この確認が示しているのは「アプリの不具合やAIの出力によって担当外が開かないこと」であって、 「接続情報を持つ者に対する防御」ではありません。

Mac Studio での実施について

今回の検証は、当方の開発機（Windows）で実施しました。今回は日程の都合で macOS 上での実施まで至っておりません。

使用している部品は PostgreSQL・Python のいずれも macOS に正式対応しており、 Apple Silicon でも同じ構成で動作する見込みです。行レベルセキュリティは PostgreSQL 本体の機能で、 OS による差はありません。OS の違いで手順が変わるのは、主として自動起動の設定（Windows のサービス登録に対し、 macOS は launchd）と文字コードの扱いで、後者はむしろ macOS のほうが素直です。

事務所内で動かす推論については、Apple Silicon のほうが有利になる見込みです。 CPU と GPU がメモリを共有する構成のため、大きめのモデルを載せやすいという事情があります。

ただし「動くこと」と「実用に足る速さで動くこと」は別の話です。後者は実機でしか測れません。 着手後の工程1で、貴所の Mac Studio 上で同じ試験一式を流し、あわせて日本語の実データで 推論と文字起こしの精度・速度・費用を実測して、結果をお出しします。 それまでは、処理性能に関する数値をお約束いたしません。
